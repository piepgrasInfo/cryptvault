## 2. cryptolib API and format 8 layout

A `scryptCostParam` overload was not in the fetched list — UNVERIFIED. https://raw.githubusercontent.com/cryptomator/cryptolib/develop/src/main/java/org/cryptomator/cryptolib/common/MasterkeyFileAccess.java
- JSON names (`@SerializedName`): `version, scryptSalt, scryptCostParam, scryptBlockSize, primaryMasterKey, hmacMasterKey, versionMac`. https://raw.githubusercontent.com/cryptomator/cryptolib/develop/src/main/java/org/cryptomator/cryptolib/common/MasterkeyFile.java
- `Cryptor`: `fileContentCryptor()`, `fileHeaderCryptor()`, `fileNameCryptor()`, `destroy()`, `close()`. https://raw.githubusercontent.com/cryptomator/cryptolib/develop/src/main/java/org/cryptomator/cryptolib/api/Cryptor.java
- `FileHeaderCryptor`: `create()`, `headerSize()`, `encryptHeader(FileHeader)`, `decryptHeader(ByteBuffer)`. https://raw.githubusercontent.com/cryptomator/cryptolib/develop/src/main/java/org/cryptomator/cryptolib/api/FileHeaderCryptor.java
- `FileContentCryptor`: `cleartextChunkSize()`, `ciphertextChunkSize()`, `encryptChunk(ByteBuffer, long chunkNumber, FileHeader)`, `decryptChunk(ByteBuffer, long chunkNumber, FileHeader, boolean authenticate)` (+ destination-buffer overloads) — random access by chunk number **confirmed**. https://raw.githubusercontent.com/cryptomator/cryptolib/develop/src/main/java/org/cryptomator/cryptolib/api/FileContentCryptor.java
- `FileNameCryptor`: `hashDirectoryId(String)`, `encryptFilename(BaseEncoding, String, byte[]... associatedData)`, `decryptFilename(...)` — directory ID goes in as associated data. https://raw.githubusercontent.com/cryptomator/cryptolib/develop/src/main/java/org/cryptomator/cryptolib/api/FileNameCryptor.java

- **Sizes/layout (docs)**: header 68 B (12 nonce + 40 payload + 16 tag); chunks up to 32 KiB cleartext, ciphertext 32 KiB + 28 B; dirs at `d/<2>/<30>` of hashed dir ID; names AES-SIV with parent dir ID as AD, base64url + `.c9r`; `dir.c9r` (dir ID), `symlink.c9r`, `dirid.c9r` (backup), `.c9s` dirs with `name.c9s`/`contents.c9r`. https://docs.cryptomator.org/en/latest/security/vault/
- **vault.cryptomator**: JWT header `kid: masterkeyfile:masterkey.cryptomator`, `alg HS256` (HS384/512 allowed); claims `format: 8`, `shorteningThreshold: 220`, `jti`, `cipherCombo: SIV_GCM|SIV_CTRMAC`; signed with enc‖mac key. **masterkey.cryptomator**: `version: 999`, scrypt fields (32768/8), `primaryMasterKey`, `hmacMasterKey`, `versionMac`. https://docs.cryptomator.org/security/architecture/

## 3. Recovery key

- Desktop `RecoveryKeyFactory`: `createRecoveryKey(Path, CharSequence)`, `validateRecoveryKey(String[, Predicate<byte[]>])`, `newMasterkeyFileWithPassphrase(Path, String, CharSequence)`; payload = 64 raw bytes + 2 bytes (16 MSBs of CRC32) = 66 B. https://raw.githubusercontent.com/cryptomator/cryptomator/develop/src/main/java/org/cryptomator/ui/recoverykey/RecoveryKeyFactory.java
- `WordEncoder`: `WORD_COUNT = 4096`, 12 bits/word, 3 B → 2 words, so 66 B → **44 words**; list `src/main/resources/i18n/4096words_en.txt`. https://raw.githubusercontent.com/cryptomator/cryptomator/develop/src/main/java/org/cryptomator/ui/recoverykey/WordEncoder.java
- Licence GPLv3 (`LICENSE.txt`). https://github.com/cryptomator/cryptomator/blob/develop/LICENSE.txt
- cryptolib develop has only `api/common/v1/v2` — **no recovery-key helper**. https://github.com/cryptomator/cryptolib/tree/develop/src/main/java/org/cryptomator/cryptolib
- Android: issue #288 "Display recovery key of a vault" still open (since 2021-03-31, milestone Backlog); docs cover recovery keys under Desktop only. Android does not show or accept a recovery key. https://github.com/cryptomator/android/issues/288

## 4. UVF status

The spec lives at encryption-alliance/unified-vault-format (develop branch, backed by Cryptomator, Cyberduck, gocryptfs, rclone); metadata file `vault.uvf` is a JWE JSON-serialization with seeds/kdf and `"uvf.spec.version": 1`; no tagged release was found. https://github.com/encryption-alliance/unified-vault-format/blob/develop/vault%20metadata/README.md — cryptolib has a `feature/uvf-draft` branch (updated 2026-08-18) with a `v3` package (`CryptorImpl`, `DirectoryContentCryptorImpl`, `DirectoryMetadataImpl`, …), nothing in 2.2.2. https://github.com/cryptomator/cryptolib/branches/all — Cyberduck merged UVF for 10.0 on 2026-04-07 using a fork artifact `ch.iterate.cryptomator:cryptolib:2.3.0.uvfdraft1`. https://raw.githubusercontent.com/iterate-ch/cyberduck/master/cryptomator/pom.xml — cryptofs has no uvf branch and desktop releases through 1.19.3 (2026-06-29) do not mention UVF; format 8 (since 1.6.0, 2021) remains the current format for new vaults. https://docs.cryptomator.org/misc/vault-format-history/

## 5. Biometric unlock in cryptomator/android

`BiometricAuthentication.kt` uses androidx `BiometricPrompt` with a `CryptoObject(cipher)` obtained from `BiometricAuthCryptor.getInstance(context, CryptoMode.GCM)`; on success it runs `encrypt(cipher, password)` / `decrypt(...)` and stores the result via `Vault.withSavedPassword(transformed, CryptoMode.GCM)` (app DB); `KeyPermanentlyInvalidatedException` / `BadPaddingException` trigger `onBiometricKeyInvalidated`. https://raw.githubusercontent.com/cryptomator/android/develop/presentation/src/main/java/org/cryptomator/presentation/util/BiometricAuthentication.kt — `BiometricAuthCryptor.java` uses `AndroidKeyStore`, alias `fingerprintCryptoKeyAccessToken_GCM` (legacy CBC alias unsuffixed), IV prepended to ciphertext. https://raw.githubusercontent.com/cryptomator/android/develop/util/src/main/java/org/cryptomator/util/crypto/BiometricAuthCryptor.java — `CryptoOperationsGCM.java`: `KeyGenParameterSpec` ENCRYPT|DECRYPT, `BLOCK_MODE_GCM`, no padding, 256-bit, `setUserAuthenticationRequired(true)`, `setInvalidatedByBiometricEnrollment(true)`; `AES/GCM/NoPadding`, 12-byte IV, 128-bit tag. https://raw.githubusercontent.com/cryptomator/android/develop/util/src/main/java/org/cryptomator/util/crypto/CryptoOperationsGCM.java

## 7. `StorageManager.openProxyFileDescriptor`

Javadoc: "Opens a seekable ParcelFileDescriptor that proxies all low-level I/O requests back to the given ProxyFileDescriptorCallback … Another useful example might be where you have an encrypted file that you're willing to decrypt on-demand"; `mode` READ_ONLY/WRITE_ONLY/READ_WRITE; `handler` "Handler that invokes callback methods" (`Preconditions.checkNotNull(handler)`); backed by `mountProxyFileDescriptorBridge()` + `FuseAppLoop`. https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/os/storage/StorageManager.java — Callback: `onGetSize()`, `onRead(long offset, int size, byte[] data)` ("must return exact requested size unless EOF"), `onWrite(...)` default-throw `EBADF`; `onFsync()` default `EINVAL`; `onRelease()` abstract. API 26. https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/os/ProxyFileDescriptorCallback.java

## Implications for the brief

- cryptolib 2.2.2 is safe on minSdk 26: Java 8 bytecode, pure Java, BouncyCastle optional/shaded; budget for Guava (~3 MB) and Gson. Pin 2.2.0 or 2.2.2, not 2.2.1 (the official app flags it as broken for file creation).
- AGPL-3.0 on cryptolib is compatible with your GPL-3.0 app, but it is stricter than GPL; keep the app GPL-3.0-or-later and note the AGPL component in licence notices.
- Random-access decryption is directly supported (`decryptChunk(chunk, n, header)` / `DecryptingReadableByteChannel(..., header, firstChunk)`), so a `ProxyFileDescriptorCallback.onRead` can map offset → chunk index; the callback runs on your Handler thread — use a dedicated `HandlerThread`.
- Recovery key must be ported from the GPL desktop code (66-byte CRC-suffixed key → 44 words from `4096words_en.txt`); it is neither in cryptolib nor in the Android app, so you would be ahead of the official client. Build on format 8; UVF is still a draft branch.
- Link fallback: Dropbox and OneDrive can link from app-scoped folders but expiry/password need paid plans (Dropbox errors `not_authorized`; OneDrive silently non-expiring on free accounts is unverified); Google Drive requires `drive.file` + a visible folder; Nextcloud is the only backend where expiry/password are free and reliable.
